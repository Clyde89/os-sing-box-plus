# Выпускная проверка os-sing-box

Этот checklist закрывал обязательные проверки готового FreeBSD-пакета на отдельном OPNsense-стенде. Regression-сценарий работал только на чтение: он не перезапускал службы, не изменял firewall и не управлял WAN. Reboot, WAN flap и имитация отказа VPN gateway выполнялись оператором в согласованное окно.

## 1. Подготовка

- Использовался отдельный OPNsense-стенд той же поддерживаемой ветки и архитектуры, что и целевая система.
- Были сохранены резервная копия OPNsense и доступ к локальной консоли.
- Были зафиксированы версия установленного пакета, состояние автозапуска и SHA-256 пользовательских `config.json` и `readiness.conf` без публикации их содержимого.
- В `readiness.conf` были заданы тестовые значения без учётных данных. Для E2E использовался домен IP-echo endpoint, входивший в policy-селектор, и заранее известный публичный IPv4 VPN.

## 2. Сборка package-артефакта

На FreeBSD или OPNsense выполнялись:

```sh
make clean
make package
pkg info -F dist/os-sing-box.pkg
sha256 dist/os-sing-box.pkg
```

Сборка считалась успешной, когда:

- SHA-256 release-артефакта и распакованного ядра совпали с зафиксированными значениями;
- `sing-box check` принял базовый sample;
- состав готового `.pkg`, режимы доступа и встроенный `build-info` прошли проверку `build.sh`;
- пакет не владел пользовательскими `config.json` и `readiness.conf`.

## 3. Обновление существующей установки

Перед обновлением повторно фиксировались контрольные суммы пользовательских файлов и состояние автозапуска. Затем пакет устанавливался штатным `pkg` в согласованное окно:

```sh
pkg add -f dist/os-sing-box.pkg
```

После установки сравнивались исходные и итоговые SHA-256 пользовательских файлов, состояние автозапуска и наличие прежнего runtime-состояния. Затем выполнялся первый выпускной шлюз:

```sh
REGRESSION_EXPECTED_PACKAGE_VERSION="1.1.0" \
REGRESSION_EGRESS_NAME="policy-ip-echo.example" \
REGRESSION_EXPECTED_EGRESS_IP="198.51.100.10" \
tests/opnsense-regression.sh --stage post-upgrade --require-managed --network
```

Тестовые домен и IPv4 в примере заменялись значениями стенда. Отчёт не должен был содержать `FAIL`.

## 4. Reboot

После успешного `post-upgrade` выполнялась контролируемая перезагрузка стенда. После восстановления OPNsense повторялся тот же regression-шлюз:

```sh
REGRESSION_EXPECTED_PACKAGE_VERSION="1.1.0" \
REGRESSION_EGRESS_NAME="policy-ip-echo.example" \
REGRESSION_EXPECTED_EGRESS_IP="198.51.100.10" \
tests/opnsense-regression.sh --stage post-reboot --require-managed --network
```

Дополнительно подтверждались отсутствие ручного вмешательства в запуск sing-box, наличие TUN, совпадение активного SHA-256 policy-плана и принадлежность TCP/UDP DNS listener текущему PID.

## 5. WAN flap

После успешного `post-reboot` оператор выполнял контролируемое отключение и восстановление WAN через штатное управление стендом. После стабилизации gateway выполнялся:

```sh
REGRESSION_EXPECTED_PACKAGE_VERSION="1.1.0" \
REGRESSION_EGRESS_NAME="policy-ip-echo.example" \
REGRESSION_EXPECTED_EGRESS_IP="198.51.100.10" \
tests/opnsense-regression.sh --stage post-wan --require-managed --network
```

Подтверждались успешный preflight, прежний PID либо корректный единственный восстановительный запуск, рабочий policy DNS bootstrap и ожидаемый VPN egress.

## 6. Fail-closed и клиентский E2E

На тестовом клиенте из выбранного селектора подтверждались:

- policy-домен разрешался через DNS redirect в FakeIP и выходил через ожидаемый VPN IPv4;
- обычный домен не попадал в policy-маршрут;
- TCP и UDP DNS-запросы обрабатывались одинаково;
- при контролируемой недоступности выбранного VPN gateway policy-трафик блокировался и не выходил через WAN;
- после восстановления gateway policy-трафик автоматически возвращался к ожидаемому VPN IPv4;
- IPv6 не создавал обходной путь, пока IPv6 policy оставался заблокированным в Apply.

Отказ gateway выполнялся только на стенде с локальной консолью. Regression-сценарий намеренно не автоматизировал это разрушительное действие.

## 7. Критерий выпуска

Ветка переводилась из draft только после одновременного выполнения условий:

- CI репозитория завершился успешно;
- готовый `.pkg` был собран на FreeBSD/OPNsense;
- `post-upgrade`, `post-reboot` и `post-wan` завершились без `FAIL`;
- контрольные суммы пользовательской конфигурации и состояние автозапуска сохранились;
- клиентский E2E и fail-closed были подтверждены на стенде;
- отчёты не содержали конфигурацию, адреса внутренних узлов, учётные данные и токены.
