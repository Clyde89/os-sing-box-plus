# os-sing-box-plus

`os-sing-box-plus` — сторонний плагин для интеграции **sing-box** с **OPNsense**.

Проект основан на `Opnwall/os-sing-box` и развивается как самостоятельный плагин с упором на предсказуемую установку, безопасное хранение конфигурации и удобное управление службой из WebUI.

> Проект находится в активной разработке и не является официальным плагином OPNsense/Deciso.

## Возможности

- интеграция службы sing-box с OPNsense;
- TUN-интерфейс `tun_singbox`;
- запуск, остановка и перезапуск службы из WebUI;
- управление автозапуском через backend `configd`;
- экспертное редактирование unmanaged-конфигурации с проверкой JSON и `sing-box check` перед сохранением;
- структурированные MVC-настройки TUN, DNS, policy outbound и селекторов трафика;
- предварительный просмотр сгенерированной runtime-конфигурации до применения;
- транзакционное применение поддерживаемой runtime-конфигурации через `configd`;
- декларативный policy-plan с проверкой SHA-256 перед активацией;
- нативные DNS redirect и filter-правила OPNsense без прямого изменения `config.xml`;
- policy routing через выбранный gateway с независимым fail-closed правилом;
- привязка активации и отката firewall-правил к жизненному циклу службы;
- безопасный базовый шаблон без тестовых прокси-узлов и учётных данных;
- сохранение пользовательской конфигурации при обновлении и удалении пакета;
- опциональная проверка готовности и восстановление после запуска системы и изменений WAN;
- просмотр и безопасная очистка журнала sing-box;
- ротация журнала через `newsyslog`;
- воспроизводимая сборка с фиксированной версией и контрольными суммами sing-box;
- сборка FreeBSD-пакета для OPNsense.

## Сборка

Сборка выполняется на FreeBSD или OPNsense:

```sh
make package
```

Готовый пакет сохраняется в каталоге `dist/`.

Бинарный файл sing-box загружается из фиксированного релиза. Перед упаковкой проверяются SHA-256 исходного release-артефакта и SHA-256 распакованного бинарного файла. Плавающие ссылки вида `releases/latest` в штатной сборке не используются. Базовый `config.json.sample` дополнительно проверяется командой `sing-box check` тем же бинарным файлом, который включается в пакет.

Готовый `.pkg` повторно проверяется после упаковки: контролируются обязательные файлы, отсутствие package-owned пользовательской runtime-конфигурации, режимы доступа и SHA-256 ядра внутри архива. Пакет устанавливает `build-info` с версией пакета, фиксированным релизом ядра, именем release-артефакта и обеими контрольными суммами без временной метки сборки.

Отдельный GitHub Actions job повторяет штатную сборку с настоящими FreeBSD 15.1, `pkg`, `fetch`, `sha256` и целевым release-артефактом. Проверенный `.pkg` и его SHA-256 публикуются как краткоживущий CI-артефакт; это не заменяет установку и E2E-проверку на OPNsense.

## Структура

- `src/` — файлы, устанавливаемые пакетом;
- `packaging/` — сценарии FreeBSD-пакета;
- `tests/` — статические и regression-проверки;
- `docs/RELEASE-CHECKLIST.md` — обязательный стендовый шлюз upgrade, reboot, WAN flap, E2E и fail-closed;
- `build.sh` — сборка пакета и формирование метаданных;
- `Makefile` — основные команды сборки.

## Конфигурация

В пакет входит только безопасный `config.json.sample`. Рабочий `config.json` создаётся из шаблона при первой установке и в дальнейшем не входит в список package-owned файлов.

При первой установке автозапуск sing-box остаётся отключённым. Служба запускается только после завершения первоначальной настройки и явного включения пользователем, поэтому установка пакета сама по себе не активирует обработку трафика.

При обновлении существующая пользовательская конфигурация и состояние автозапуска временно сохраняются до замены файлов старого пакета и восстанавливаются после установки новой версии. Это защищает `config.json` и существующий режим работы при переходе со старой схемы пакета.

Основной пункт меню sing-box открывает структурированный MVC WebUI. Отдельная страница службы и экспертного JSON сохранена для диагностики, управления процессом и совместимости с unmanaged-конфигурацией. Перед сохранением ручных изменений выполняются проверка JSON и `sing-box check`; после включения managed-режима редактор остаётся доступным только для просмотра, а запись блокируется общей с транзакционным Apply файловой блокировкой и повторной серверной проверкой состояния.

Структурированная MVC-модель хранит параметры TUN/DNS, policy outbound, policy DNS bootstrap и селекторы трафика отдельно от ручного JSON. Для списков предусмотрены многострочные поля: доменные имена вводятся по одному на строку, а клиенты поддерживают отдельные IPv4/IPv6-адреса, CIDR и диапазоны адресов. Интерфейсы захвата выбираются отдельно; WAN намеренно исключён из автоматического захвата.

Структурированные настройки разделяют операции **сохранения**, **предварительного просмотра** и **применения**. Сохранение MVC-модели не изменяет рабочий `config.json`. Предварительный просмотр формирует JSON, декларативный policy-план OPNsense и SHA-256 без изменения runtime-состояния. Применение выполняется через `configd`, блокирует параллельные операции, использует временный файл, проверяет результат командой `sing-box check`, создаёт резервную копию и только затем атомарно заменяет рабочую конфигурацию. Если служба работала, она синхронно перезапускается, активный policy-план проверяется по SHA-256, а ошибка восстанавливает предыдущие runtime-файлы, managed-состояние и службу.

Перед Apply выполняется fail-closed сетевой preflight по фактическому состоянию OPNsense. Проверяются существование и состояние выбранных LAN/VLAN-интерфейсов, назначение DNS-listener и `bindAddress` локальным адресам, наличие активного IPv4 gateway, корректность TUN-адреса, а также пересечения FakeIP/TUN с локальными сетями. Некорректный порт не заменяется значением по умолчанию. Ошибки отображаются в preview и блокируют изменение runtime-файлов и перезапуск службы.

Для выбранных доменов формируются IPv4 FakeIP-конфигурация и отдельный `policy-out` типа `direct` с настраиваемой `inet4_bind_address`. Трафик FakeIP направляется в этот outbound, а конкретный исходящий адрес и gateway задаются пользователем и не вшиваются в пакет.

Для внутреннего разрешения доменов `policy-out` использует настраиваемый DNS over HTTPS server `policy-dns`. Его соединение проходит через отдельный source-bound outbound `policy-dns-bootstrap`, который намеренно не содержит `domain_resolver`. Такая топология исключает рекурсивную зависимость DNS transport от самого policy DNS. IPv4-адрес upstream DNS, порт, TLS-имя и HTTP-путь задаются через WebUI; конкретные сетевые значения в пакет не вшиваются.

При применении режима `selected` сохраняется декларативный policy-plan версии `2`. После успешного запуска TUN служба подтверждает принадлежность TCP- и UDP-сокетов DNS listener текущему PID `sing-box`, активирует план по SHA-256 и запрашивает штатную перезагрузку firewall OPNsense. До успешной readiness-проверки DNS redirect, policy route и fail-closed не включаются. Через нативный API регистрируются перенаправления UDP/TCP DNS для выбранных IPv4-клиентов и интерфейсов, policy route через выбранный gateway и следующее за ним независимое fail-closed правило. При отсутствующем gateway policy route пропускается, а fail-closed правило сохраняется.

FakeIP-сеть маршрутизируется самим TUN sing-box через `auto_route` и ограниченный `route_address`; отдельный системный маршрут OPNsense не создаётся. При остановке службы управляемые firewall-правила отключаются до завершения процесса. Ошибка firewall reload восстанавливает прежний признак активности и блокирует небезопасное продолжение операции.

Режим `all_lan` формируется только для предварительного просмотра и остаётся заблокированным для Apply до отдельного явного подтверждения. Текущий policy-контур работает только с IPv4/A-запросами. IPv6-селекторы сохраняются в модели, но блокируют применение до добавления отдельной IPv6-реализации.

Существующая пользовательская `config.json`, созданная вне MVC-механизма, не перезаписывается автоматически. Явное подтверждение перехода в WebUI сохраняет защищённую исходную копию и создаёт одноразовое разрешение, связанное с текущей SHA-256. Подтверждение не меняет рабочий файл и не перезапускает службу. Следующий успешный транзакционный Apply включает managed-режим; изменение исходного JSON после подтверждения автоматически блокирует переход до повторной проверки.

## Восстановление после сетевых изменений

Пакет содержит механизм проверки готовности sing-box после запуска системы и событий IPv4 `newwanip`. По умолчанию он отключён и не содержит адресов или доменов конкретной сети.

После явной настройки механизм проверяет доступность underlay, policy DNS и сквозной E2E-поток. Если underlay доступен, а policy-маршрут не работает, выполняется один восстановительный перезапуск sing-box с повторной проверкой результата.

Параметры задаются в `readiness.conf`, который создаётся из безопасного `readiness.conf.sample` только при отсутствии пользовательского файла.

## Статус

Для проверки установленного package-артефакта добавлен read-only сценарий `tests/opnsense-regression.sh`. Он проверяет `pkg check -s`, происхождение и SHA-256 ядра, права доступа, `sing-box check`, службу, PID, TUN, сетевой preflight, managed policy, активный SHA-256 и TCP/UDP readiness DNS listener. Опциональный режим `--network` подтверждает policy DNS bootstrap и ожидаемый VPN egress без перезапуска службы.

До первого самостоятельного релиза оставлены обязательными фактические прогоны `post-upgrade`, `post-reboot`, `post-wan`, клиентский E2E и контролируемый fail-closed на OPNsense-стенде. Точный порядок и критерии описаны в [выпускном checklist](docs/RELEASE-CHECKLIST.md).
